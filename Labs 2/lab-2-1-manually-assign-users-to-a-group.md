# Lab 2.1 — Manually Assign Users to a Group

**Path:** Organize Users with Groups  
**Platform:** Okta Admin 
**Status:** ✅ Completed

---

## Objective

Create a group in Okta, manually assign users to it, and verify the
membership and event log entries generated by those actions.

---

## Business scenario

The organization needs a dedicated group for its executive team. Executive
users require access to a distinct set of applications and will be subject
to more restrictive authentication policies than standard employees.
Before those policies can be applied, the group must exist and the correct
users must be members.

As the IAM administrator, I created the Executives group, assigned three
users — Jay Kumar, Sarah James, and Ping Yang — and verified the group
membership and event log trail.

This lab establishes the Executives group that is referenced across
subsequent labs in Path 2, where group membership is used as a condition
for automated rule-based assignments.

---

## What I configured

### Step 1 — Created the Executives group

From the Okta Admin Console, I navigated to **Directory > Groups** and
added a new group with the following values:

| Field | Value |
|-------|-------|
| Name | Executives |
| Description | Executive team |

After saving, I refreshed the browser to confirm the group appeared in
the directory.

**Why the description matters:**  
Group descriptions are not just labels — they are governance artifacts.
In a production environment with hundreds of groups, a clear description
is what allows an administrator unfamiliar with the group to understand
its purpose without needing to open a separate ticket or ask a colleague.
Undescribed groups accumulate over time and become a governance liability.

### Step 2 — Manually assigned users to the group

I selected the Executives group, chose **Assign people**, and added the
following users:

- Jay Kumar
- Sarah James
- Ping Yang

Each user was located using the search function and added with the **+**
button. After selecting **Done**, I verified that all three users appeared
in the Executives group member list.

### Step 3 — Verified the event log

From the Executives group, I selected **View logs** and confirmed the
system log captured the following events:

| Event | Target | Result |
|-------|--------|--------|
| Create Okta group | Executives (UserGroup) | SUCCESS |
| Add user to group membership | Jay Kumar (User) / Executives (UserGroup) | SUCCESS |
| Add user to group membership | Sarah James (User) / Executives (UserGroup) | SUCCESS |
| Add user to group membership | Ping Yang (User) / Executives (UserGroup) | SUCCESS |

Every group creation and membership change is a logged event in Okta.
This audit trail is what compliance teams reference to answer the question:
*who was added to this group, by whom, and when?*

## Manual vs. rule-based group assignment

This lab uses manual assignment — an administrator explicitly adds each
user to the group. Manual assignment is straightforward but does not
scale, and it introduces human error as a risk factor.

The subsequent labs in Path 2 introduce rule-based assignment, where group
membership is determined automatically by conditions such as group
membership inheritance or user profile attributes. Understanding manual
assignment first provides the baseline that makes rule-based automation
meaningful by contrast.

| Assignment method | How it works | Best for |
|-------------------|-------------|----------|
| Manual | Admin explicitly adds each user | Small, stable groups; special-purpose access |
| Rule-based (group membership) | Users added to Group A are automatically added to Group B | Nested access structures; role hierarchies |
| Rule-based (user attribute) | Users are assigned based on profile attributes (department, region, etc.) | Large orgs; attribute-driven access |
| Rule-based (OEL expression) | Multi-condition logic determines membership | Complex filtering; combined attribute and type conditions |

Manual assignment remains appropriate in production for certain use cases:
executive access, emergency break-glass accounts, and pilot groups used
for phased policy rollouts — all of which appear in later labs in this
repository.

## Why this matters

**Groups are the primary mechanism for scaling access control in Okta.**
Rather than assigning applications and policies to individual users,
organizations assign them to groups. A user's access is determined by
their group memberships. This means group integrity — knowing who is
in each group and why — is fundamental to the organization's security
posture.

**Manual group management is a governance risk at scale.** When group
membership is maintained manually, access accumulates over time. Users
change roles, leave departments, or leave the company — but their group
memberships often persist unless someone remembers to remove them. This
is access drift, and it is one of the most common findings in IAM audits.
The rule-based automation introduced in Labs 2.2 through 2.4 addresses
this risk directly.

**The event log is the answer to "who has access and how did they get it."**
Every manual group assignment is captured with a timestamp and, in a
production environment, the identity of the administrator who performed
the action. This is the chain of evidence that compliance and security
teams rely on. Administrators who verify log entries after membership
changes are building audit-ready habits.

**Pilot groups are a security deployment pattern, not just a lab concept.**
In Labs 3.5 and 3.8, a "Pilot Users" group is used to test new
authentication and enrollment policies before rolling them out to the
entire organization. This pattern — create a group, add a controlled set
of users, apply a policy scoped to that group, verify behavior, then
expand — is standard enterprise change management practice for IAM
policy deployment.

## Lessons learned

The most significant insight from this lab was not the configuration
itself — creating a group and adding users is straightforward. What stood
out was the event log. Seeing each individual membership addition captured
as a discrete, timestamped event made the audit trail feel real rather
than abstract. In a production environment where hundreds of group changes
happen weekly, the system log is the only reliable record of how access
was granted.

The manual assignment method also highlighted its own limitation. Adding
three users to one group took only a few minutes. Imagining the same
process for fifty users across twenty groups — with no automation — made
the value of rule-based assignment immediately obvious. This lab set up
that contrast deliberately, and it landed.

The group description decision was also worth noting. Writing "Executive
team" as the description took five seconds and will save future
administrators from having to investigate what the group is for. In a
real environment where group proliferation is common, this discipline
at creation time is a small investment with compounding returns.
